## فاز ۱ — ویزارد پویا: مراحل سفارشی

**هدف:** مدیر بتواند علاوه بر فیلدها، **مرحلهٔ جدید** هم به ویزارد ثبت‌نام اضافه کند
(مثلاً «مرحلهٔ ۵: سوابق بیمه» بین مراحل موجود یا در انتها).

### شرح
- تعریف مرحله (عنوان، آیکون، شرح، ترتیب، فعال بودن) از پنل مدیریت.
- فیلدهای هر مرحله از همان فرم‌ساز موجود (`form_fields`) با `step` پویا تأمین می‌شوند.
- ویزارد عمومی به‌جای ۴ مرحلهٔ ثابت، مراحل فعال را از پایگاه داده می‌خواند؛
  استپر و نوار پیشرفت بر اساس تعداد مراحل محاسبه می‌شود.
- ذخیرهٔ مرحله‌ای در سشن با کلید پویا؛ اعتبارسنجی هر مرحله پیش از عبور.

### تغییرات داده
```sql
CREATE TABLE wizard_steps (
  id INT AUTO_INCREMENT PRIMARY KEY,
  title VARCHAR(100) NOT NULL,
  description TEXT NULL,
  icon VARCHAR(30) NULL,          -- نام آیکون از دیکشنری icon()
  step_position INT NOT NULL,     -- جایگاه در ویزارد
  is_system TINYINT(1) DEFAULT 0, -- چهار مرحلهٔ فعلی سیستمی می‌مانند
  is_active TINYINT(1) DEFAULT 1,
  sort_order INT DEFAULT 0
);
-- form_fields.step به wizard_steps.id ارجاع پیدا می‌کند (مهاجرت تدریجی)
```

### نکات فنی
- مراحل سیستمی (۱ تا ۴ فعلی) حذف‌شدنی نیستند؛ مراحل سفارشی بین آن‌ها یا پس از مرحلهٔ ۳
  (پیش از بارگذاری مدارک که همیشه آخرین است) درج می‌شوند.
- کشش مسیر: `GET /register/step/{n}` به‌جای مسیرهای سخت‌کد.

## فاز ۲ — بارگذاری مدرک جدید توسط متقاضی (پس از ثبت)

**هدف:** متقاضی بتواند **پس از اخذ کد رهگیری** مدرک جدیدی به پرونده اضافه کند
(مثلاً مدرک اصلاح‌شده پس از «درخواست اصلاح مدارک»).

### قاعدهٔ کسب‌وکاری (مهم)
طبق نیازمندی اعلام‌شده: بارگذاری مدرک جدید تنها در صورتی مجاز است که
**تمامی اطلاعات قبلی پرونده نیز قابل ویرایش/بازبینی باشد** — یعنی پرونده از حالت
«قفلِ پس از ثبت» خارج شده و یک چرخهٔ «بازبینی کامل» آغاز شود:

1. متقاضی در صفحهٔ پیگیری دکمهٔ «درخواست افزودن/اصلاح مدرک» را می‌زند.
2. سیستم یک «چرخهٔ بازبینی» (Revision) باز می‌کند: فرم‌های مراحل ۱ تا ۴
   با داده‌های فعلی **پیش‌پر** شده و برای متقاضی قابل ویرایش می‌شوند.
3. متقاضی تغییرات را ثبت می‌کند؛ رویداد «ثبت نسخهٔ بازبینی» در تایم‌لاین درج می‌شود.
4. مدیر در پنل، نسخهٔ بازبینی را در کنار نسخهٔ اصلی می‌بیند (diff ساده: تغییرات هایلایت)
   و تأیید/رد می‌کند. تا تأیید مدیر، دادهٔ رسمی پرونده همان نسخهٔ قبلی است.

### تغییرات داده
```sql
CREATE TABLE applicant_revisions (
  id INT AUTO_INCREMENT PRIMARY KEY,
  applicant_id INT NOT NULL,
  payload JSON NOT NULL,            -- کل دادهٔ پیشنهادی (مراحل ۱-۳ + فهرست مدارک جدید)
  status ENUM('در انتظار','تأیید شده','رد شده') DEFAULT 'در انتظار',
  reviewed_by INT NULL, reviewed_at DATETIME NULL,
  note VARCHAR(255) NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (applicant_id) REFERENCES applicants(id) ON DELETE CASCADE
);
```

### نکات امنیتی
- محدودسازی نرخ (مثلاً ۲ بازبینی در هفته) و ممنوعیت بازبینی وقتی پرونده
  «در انتظار بازبینی» دارد.
- مدارک جدید با همان لایه‌های امنیتی فعلی (MIME واقعی، نام تصادفی، خارج از public).

## فاز ۳ — گردش پرداخت هزینهٔ ثبت‌نام (رسید پرداخت)

**هدف:** پس از اطلاع‌رسانی متقاضی به مدیر و **تأیید مدارک توسط مدیر**، امکان
بارگذاری **تصویر رسید پرداخت** فراهم شود.

### جریان کار
```
تکمیل اطلاعات ← تأیید مدارک توسط مدیر ← صدور «فرصت پرداخت» برای متقاضی
  ← نمایش کانال‌های پرداخت در صفحهٔ پیگیری ← واریز توسط متقاضی
  ← بارگذاری تصویر رسید + انتخاب کانال پرداخت ← بررسی مدیر (تأیید/رد)
  ← ادامهٔ فرآیند صدور مجوز
```

### انتخاب کانال پرداخت توسط کاربر
هنگام بارگذاری رسید، متقاضی مشخص می‌کند وجه را از کدام کانال واریز کرده است:
- **کارت‌به‌کارت** (شمارهٔ کارت + نام دارنده — از تنظیمات خوانده می‌شود)
- **حساب بانکی / شبا** (شمارهٔ حساب، شبا، بانک)
- **پرداخت اینترنتی** (لینک درگاه — در فازهای بعد با اتصال به PSP واقعی)

**کانال‌های پرداخت از پنل مدیریت قابل افزودن/ویرایش/حذف/غیرفعال‌سازی هستند.**

### تغییرات داده
```sql
CREATE TABLE payment_channels (
  id INT AUTO_INCREMENT PRIMARY KEY,
  title VARCHAR(100) NOT NULL,        -- مثال: «کارت بانک ملت به نام ...»
  channel_type ENUM('کارت به کارت','حساب بانکی','پرداخت اینترنتی','سایر') NOT NULL,
  account_info TEXT NULL,             -- شمارهٔ کارت/حساب/شبا/لینک درگاه
  is_active TINYINT(1) DEFAULT 1,
  sort_order INT DEFAULT 0
);

CREATE TABLE payments (
  id INT AUTO_INCREMENT PRIMARY KEY,
  applicant_id INT NOT NULL,
  payment_channel_id INT NULL,
  amount BIGINT UNSIGNED NULL,        -- تومان
  receipt_document_id INT NULL,       -- ارجاع به جدول documents (تصویر رسید)
  reference_code VARCHAR(50) NULL,    -- کد رهگیری بانکی/پیگیری درگاه
  paid_at DATETIME NULL,              -- تاریخ واریز اعلامی کاربر
  status ENUM('در انتظار بررسی','تأیید شده','رد شده') DEFAULT 'در انتظار بررسی',
  reviewed_by INT NULL, reviewed_at DATETIME NULL, reject_reason VARCHAR(255) NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (applicant_id) REFERENCES applicants(id) ON DELETE CASCADE,
  FOREIGN KEY (payment_channel_id) REFERENCES payment_channels(id) ON DELETE SET NULL
);
```

### نکات
- نمایش «فرصت پرداخت» منوط به پرچم `payment_required` روی پرونده و تأیید مدارک است.
- اتصال به درگاه واقعی (زرین‌پال/پی‌پال ایرانی/… خارج از دامنهٔ «بدون کتابخانهٔ خارجی» است)؛
  فعلاً رسید-محور (Manual Approval) طراحی شود — الگوی رایج در سامانه‌های دولتی ایران.

## فاز ۴ — بخش «درآمد» در پنل مدیریت

**هدف:** مدیریت متمرکز پرداخت‌های کاربران + تعریف کانال پرداخت + گزارش مالی.

### امکانات
- فهرست پرداخت‌ها با فیلتر (وضعیت، کانال، بازهٔ تاریخ شمسی، مبلغ) و صفحه‌بندی.
- تأیید/رد رسید با ثبت دلیل و نام بررسی‌کننده (الگوی همان گردش کد پستی).
- کارت‌های آماری: درآمد تأییدشدهٔ امروز/هفته/ماه (شمسی)، در انتظار بررسی، ردشده‌ها.
- گزارش گروه‌بندی‌شده: درآمد بر اساس کانال پرداخت / رشتهٔ مجوز / ماه.
- خروجی CSV + نسخهٔ چاپی گزارش مالی.
- مدیریت کانال‌های پرداخت (CRUD) — همان‌جا که کاربر کانال را انتخاب می‌کند.

### جدول
همان `payments` و `payment_channels` فاز ۳ + ویوهای تجمیعی SQL.

## فاز ۵ — ثبت پیامک‌های وضعیت توسط متقاضی

**هدف:** سازمان صادرکننده به متقاضی **پیامک** می‌زند؛ متقاضی متن/کد پیامک را
در سامانه وارد می‌کند و وضعیت پرونده (پس از **تأیید مدیر**) به‌روز می‌شود.

### جریان کار
1. متقاضی در صفحهٔ پیگیری: «ثبت پیامک دریافتی» → انتخاب «نوع پیامک» از فهرست
   الگوهای تعریف‌شده + ورود کد/متن پیامک + تاریخ دریافت (شمسی).
2. رکورد با وضعیت «در انتظار تأیید» ثبت و رویداد در تایم‌لاین درج می‌شود.
3. مدیر در پنل (صفحهٔ «پیامک‌های ثبت‌شده») صحت آن را بررسی و تأیید می‌کند.
4. **پس از تأیید**، وضعیت پرونده به وضعیت نگاشت‌شدهٔ آن الگو ارتقا می‌یابد
   (با رعایت مسیر یکطرفهٔ موجود و ثبت در `status_log`).

### تغییرات داده
```sql
CREATE TABLE sms_templates (          -- الگوهای پیامک (متن + وضعیت مقصد)
  id INT AUTO_INCREMENT PRIMARY KEY,
  title VARCHAR(120) NOT NULL,         -- مثال: «پیامک پذیرش نهایی سازمان»
  sample_text TEXT NULL,               -- نمونهٔ متن برای راهنمای کاربر
  target_status VARCHAR(50) NOT NULL,  -- وضعیت مقصد پس از تأیید مدیر
  requires_code TINYINT(1) DEFAULT 0,  -- آیا ورود کد پیامک الزامی است
  is_active TINYINT(1) DEFAULT 1,
  sort_order INT DEFAULT 0
);

CREATE TABLE user_sms_entries (
  id INT AUTO_INCREMENT PRIMARY KEY,
  applicant_id INT NOT NULL,
  sms_template_id INT NOT NULL,
  sms_code VARCHAR(50) NULL,
  sms_text TEXT NULL,
  received_at DATE NULL,               -- تاریخ شمسی→میلادی ذخیره می‌شود
  status ENUM('در انتظار','تأیید شده','رد شده') DEFAULT 'در انتظار',
  reviewed_by INT NULL, reviewed_at DATETIME NULL, reject_reason VARCHAR(255) NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (applicant_id) REFERENCES applicants(id) ON DELETE CASCADE
);
```

### نکات
- **متن الگوها و وضعیت‌های مقصد تماماً از پنل مدیریت قابل افزودن/ویرایش/حذف هستند.**
- محدودسازی نرخ ثبت پیامک (ضد اسپم): مثلاً ۳ ثبت در روز.
- اعتبارسنجی نگاشت: `target_status` باید در فهرست وضعیت‌های مجاز (config/statuses.php) باشد.

## فاز ۶ — تصویر مجوز صادرشده و قاعدهٔ «یک‌بار دریافت»

**هدف:** پس از «صدور مجوز»، مدیر تصویر مجوز را در پروفایل متقاضی بارگذاری می‌کند
و لینک دسترسی امن برای متقاضی فعال می‌شود.

### قواعد
1. **دریافت اول رایگان/خودکار:** با رسیدن وضعیت به «صدور مجوز» و بارگذاری تصویر توسط مدیر،
   متقاضی یک‌بار لینک مشاهده/دانلود تصویر مجوز را در صفحهٔ پیگیری می‌بیند.
2. **دفعات بعد:** لینک پس از دریافت اول قفل می‌شود؛ متقاضی «درخواست دریافت مجدد تصویر مجوز»
   ثبت می‌کند → مدیر مطلع می‌شود → در صورت نیاز **پرداخت هزینه** (وصل به گردش پرداخت فاز ۳)
   → پس از تأیید مدیر، لینک برای مدت محدود (مثلاً ۷۲ ساعت) دوباره فعال می‌شود.
3. لینک‌ها یک‌بارمصرف/زمان‌دار با توکن تصادفی (`random_bytes`) — نه آدرس ثابت.

### تغییرات داده
```sql
CREATE TABLE license_files (
  id INT AUTO_INCREMENT PRIMARY KEY,
  applicant_id INT NOT NULL,
  document_id INT NOT NULL,            -- تصویر مجوز در جدول documents
  issued_at DATETIME NULL,
  download_count INT DEFAULT 0,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (applicant_id) REFERENCES applicants(id) ON DELETE CASCADE,
  FOREIGN KEY (document_id) REFERENCES documents(id) ON DELETE CASCADE
);

CREATE TABLE license_access_requests (
  id INT AUTO_INCREMENT PRIMARY KEY,
  applicant_id INT NOT NULL,
  access_token CHAR(64) NOT NULL UNIQUE,   -- توکن یک‌بارمصرف لینک
  payment_id INT NULL,                     -- پرداخت مرتبط (در صورت هزینه)
  status ENUM('در انتظار','تأیید شده','رد شده','منقضی') DEFAULT 'در انتظار',
  expires_at DATETIME NULL,
  reviewed_by INT NULL, reviewed_at DATETIME NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (applicant_id) REFERENCES applicants(id) ON DELETE CASCADE
);
```

### سرو فایل
کنترلر اختصاصی `LicenseFileController` با بررسی: نشست/توکن معتبر + انقضا +
تعداد دفعات + وضعیت پرداخت — مشابه الگوی امن `DocumentController` فعلی.

## فاز ۷ — چندمجوزی و سلسله‌مراتب پرونده‌ها

**هدف:** یک متقاضی (کد ملی) بتواند **چندین مجوز** داشته باشد:
- درخواست‌های همزمان در رشته‌های متفاوت
- پرونده‌های قدیمیِ «باطل/منقضی‌شده» که دسترسی‌شان حفظ می‌شود
- زنجیرهٔ تمدید/ارتقا: پروندهٔ جدید به پروندهٔ قبلی «والد» ارجاع می‌شود

### تغییرات ساختاری (مهاجرت بزرگ)
```sql
-- تفکیک «شخص» از «پرونده/مجوز»
CREATE TABLE persons (
  id INT AUTO_INCREMENT PRIMARY KEY,
  national_code CHAR(10) NOT NULL UNIQUE,
  first_name VARCHAR(50) NOT NULL, last_name VARCHAR(50) NOT NULL,
  father_name VARCHAR(50) NULL, birth_date DATE NULL,
  mobile CHAR(11) NOT NULL, postal_code CHAR(10) NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_mobile (mobile)
);

ALTER TABLE applicants
  ADD COLUMN person_id INT NULL AFTER id,
  ADD COLUMN parent_application_id INT NULL,       -- سلسله‌مراتب (تمدید/ارتقا)
  ADD COLUMN license_state ENUM('جاری','صادر شده','باطل شده','منقضی') DEFAULT 'جاری',
  ADD COLUMN license_valid_until DATE NULL,        -- تاریخ انقضای اعتبار مجوز
  MODIFY national_code CHAR(10) NULL;               -- یکتایی به persons منتقل می‌شود
```

### قواعد
- یکتایی فعلی `national_code` و `mobile` روی `applicants` **برداشته** و به `persons` منتقل می‌شود؛
  هر person می‌تواند چند applicant (پرونده) داشته باشد.
- کد رهگیری همچنان به ازای هر **پرونده** یکتاست.
- لغو/ابطال یک پرونده، سایر پرونده‌های شخص را تحت تأثیر قرار نمی‌دهد.
- «لغو خودکار ۱۴ روزه» بدون تغییر per-application باقی می‌ماند.
- سازگاری عقب‌رو (Backward-compat): برای هر رکورد فعلی applicants یک person
  ساخته و متصل می‌شود (اسکریپت مهاجرت داده).

## فاز ۸ — سابقهٔ متقاضی با احراز هویت اطلاعات هویتی

**هدف:** متقاضی بدون حساب کاربری، **سوابق خود** (همهٔ مجوزهای جاری، صادرشده و باطل)
را ببیند — منوط به تطبیق چندعاملی اطلاعات هویتی.

### مکانیزم احراز (بدون رمز عبور)
فرم «مشاهدهٔ سوابق» با فیلدهای: **کد ملی + نام + نام خانوادگی + نام پدر + موبایل + تاریخ تولد (شمسی)**.
- همهٔ شش عامل باید با رکورد `persons` مطابقت دقیق داشته باشند.
- محدودسازی نرخ سخت‌گیرانه (مثلاً ۳ تلاش در ۱۰ دقیقه + قفل تصاعدی) — چون این
  نقطه، هدف اصلی حدس زدن اطلاعات هویتی است.
- در صورت تطبیق: فهرست پرونده‌ها با وضعیت، کد رهگیری، رشته و تاریخ صدور + لینک تایم‌لاین.
- لاگ امنیتی: هر تلاش ناموفق با IP و زمان در `security_log` ثبت شود (پایش سوءاستفاده).

```sql
CREATE TABLE identity_checks (
  id INT AUTO_INCREMENT PRIMARY KEY,
  national_code CHAR(10) NOT NULL,
  ip VARCHAR(45) NULL,
  success TINYINT(1) NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_nc_time (national_code, created_at)
);
```

> نکتهٔ حریم خصوصی: فقط «تطبیق» انجام می‌شود؛ هیچ داده‌ای پیش از احراز نمایش داده نمی‌شود
> و پاسخ خطا یکسان است («اطلاعات تطبیق نیافت») تا وجود/عدم وجود رکورد نشت نکند.

## فاز ۹ — گسترش انواع خدمات (فراتر از صنایع دستی)

**هدف:** سامانه بستر ثبت درخواست برای سایر مجوزها هم بشود:

| سرویس | مرجع صدور (بر پایهٔ منابع رسمی) | مدارک/مراحل شاخص |
|---|---|---|
| **مجوز مشاغل خانگی (مستقل)** | وزارت تعاون، کار و رفاه اجتماعی — سامانهٔ مشاغل خانگی `mkh.mcls.gov.ir` (ثبت‌نام، سپس ارجاع به دستگاه اجرایی رشته) | همان مدارک فعلی کفایت می‌کند؛ شرایط عمومی: تابعیت ایران، سن قانونی، کارت پایان خدمت/معافیت (مردان)، سکونت در محل اجرای طرح |
| **مجوز شغل خانگی (پشتیبان)** | همان سامانه — نقش پشتیبان: حمایت از چند شاغل خانگی (آموزش، تأمین مواد اولیه، بازاریابی و فروش) | **اطلاعات بیشتر:** طرح توجیهی کسب‌وکار، فهرست و مشخصات افراد تحت پوشش، جزئیات درآمدی، حداقل ۵ سال سابقهٔ مرتبط، تأمین ≥۲۰٪ سرمایهٔ اولیه، حداقل ۲۰ سال سن، نداشتن سوءپیشینهٔ مؤثر |
| **مجوزهای گردشگری** | وزارت میراث فرهنگی، گردشگری و صنایع دستی — ثبت درخواست از «درگاه ملی مجوزها» و سامانهٔ جانا `myst.mcth.ir` (اقامتگاه بوم‌گردی، تأسیسات گردشگری، دفتر خدمات مسافرتی بندهای الف/ب/پ) | موافقت‌نامهٔ اصولی → پروانهٔ بهره‌برداری؛ مدارک مالکیت/اجارهٔ محل، تأییدیهٔ اماکن، گواهی مدیریت تأسیسات |
| **مجوزهای هنری/فرهنگی** | وزارت فرهنگ و ارشاد اسلامی — پنجرهٔ واحد خدمات «وفا» و سامانه‌های آموزشگاه‌های آزاد هنری/کارت صلاحیت تدریس | بسته به زیررشته: گواهی مهارت، برنامهٔ آموزشی، مدارک محل فعالیت |

### طراحی فنی
- جدول `service_types` (شناسه، عنوان، مرجع صدور، فعال بودن) و افزودن `service_type_id`
  به پرونده‌ها؛ فرم‌ساز فعلی **per-service** می‌شود: هر سرویس، مراحل/فیلدهای/مدارک
  الزامی مخصوص خودش را دارد (زیرساخت `form_fields.step` و گروه‌بندی موجود، قابل توسعه است).
- «قالب پیام اطلاع‌رسانی» و راهنما per-service قابل تنظیم شوند.
- گزارش‌ها بُعد جدید «نوع سرویس» می‌گیرند.

### تطبیق با قانون تسهیل صدور مجوزها
طبق «قانون تسهیل صدور مجوزهای کسب‌وکار» (۱۳۹۰) و درگاه ملی مجوزها (`mojavez.gov.ir`)،
ثبت درخواست در درگاه به‌منزلهٔ شروع فرآیند رسمی است و دستگاه‌ها موظف به پاسخ‌گویی
زمان‌بندی‌شده‌اند. طراحی وضعیت‌های زمان‌محور سامانه (لغو ۱۴ روزه و هشدار «در آستانهٔ لغو»)
باید با مهلت‌های قانونی درگاه ملی هم‌راستا نگه داشته شود (قابل پیکربندی per-service باشد).

## فاز ۱۰ — اشخاص حقوقی

**هدف:** پشتیبانی از ثبت مجوز برای **شرکت‌ها/تعاونی‌ها** (اشخاص حقوقی) با مدارک و مراحل متفاوت.

### تفاوت‌های کلیدی نسبت به شخص حقیقی
| بخش | شخص حقیقی (وضع فعلی) | شخص حقوقی (جدید) |
|---|---|---|
| هویت | کد ملی، نام پدر، تولد | **شناسهٔ ملی شخص حقوقی (۱۱ رقمی)**، نام شرکت، شمارهٔ ثبت، تاریخ ثبت، نوع شخصیت (شرکت خصوصی/تعاونی/مؤسسه) |
| نماینده | — | مشخصات کامل نمایندهٔ مجاز (کد ملی، سمت) + روزنامهٔ رسمی/وکالت‌نامه |
| اساسنامه | — | تصویر اساسنامه و آخرین تغییرات |
| مالی | — | کد اقتصادی، گواهی ارزش افزوده (در صورت لزوم) |
| مجوز خانگی پشتیبان | — | طرح توجیهی + فهرست افراد تحت پوشش + جزئیات درآمدی (نگاه کنید به فاز ۹) |

### طراحی فنی
- `applicant_type ENUM('حقیقی','حقوقی')` روی پرونده‌ها.
- فرم‌ساز پویا شرطی: فیلدهای دارای `visible_when` (JSON) — مثلاً فیلدهای شخص حقوقی
  فقط وقتی `applicant_type='حقوقی'` نمایش داده شوند (الگوی نمایش مشروط
  «وضعیت مالکیت → نوع مدرک» در مرحلهٔ ۴ هم‌اکنون به‌شکل ساده وجود دارد و قابل تعمیم است).
- اعتبارسنجی شناسهٔ ملی حقوقی: الگوریتم رقم کنترل ۱۱ رقمی (مشابه کد ملی حقیقی
  اما با وزن‌های متفاوت) — پیاده‌سازی در `Validator`.
- مدارک الزامی per-type در `form_fields` با پرچم `applies_to ENUM('both','individual','legal')`.

| اولویت | فاز | برآورد نسبی | ارزش افزوده |

| 🔴 بالا | فاز ۶ (تصویر مجوز + قاعدهٔ یک‌بار دریافت) | متوسط | تکمیل چرخهٔ صدور |

ترتیب اجرا بهتر است ۳ → ۴ → ۶ → ۵ → ۲ → ۷ → ۸ → ۱ → ۹ → ۱۰ باشد.
